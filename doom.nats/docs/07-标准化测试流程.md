# 07 · 标准化测试流程

> 目标：任何一次改动，都能用**同一套命令**跑完、并且**留下机器可读的证据**。
> 三层防线：静态（`verify.mjs`）→ 无头模拟（`sim.mjs`）→ 进游戏实测（本流程）。
> 前两层在 `05-静默验证报告.md`；本文只管第三层 —— 真游戏、真日志。

## 1. 进游戏：P0 → P1 → P2 一条龙

进世界后**按顺序**执行；每条都会往聊天栏写带前缀的行，供第 2 步抽取。

```mcfunction
/reload                        # 加载包（新装的包必须先 reload）
/function nats.debug:p0        # P0 加载期断言（自动，十几条）
/function nats.debug:on        # 打开开关 + 确认 $period/$cap
/function nats.debug:sample    # P1 生成 3 只样例实体，肉眼核对 NBT 语义
/function nats.debug:accel     # P2 逻辑加速（period=1 / repeat=40）
/function nats.debug:burst     # P2 快进 200 次主逻辑（≈10 秒游戏时间）
/function nats.debug:state     # 看 $t / $enable / $period 等
/function nats.debug:count     # 看已刷实体数 vs $cap
/function nats.debug:dump      # 一次性打印全部数值
/function nats.debug:resume    # 还原默认节拍 period=5 / repeat=10 / cap=70
```

`nats.debug:sample` 的核对清单见 `06-进游戏实测清单.md`（① 永久力量 ② 弓+掉落率 ③ 头颅贴图+属性）。
`nats.debug:wipe` 清场：删掉 `suso.nats.count` 实体与 `nats.sample` 实体并把计数归零。

### 单人客户端**没有**的命令

`tick freeze` / `tick sprint` / `tick rate` 是**专用服务器**命令。写进函数里的后果不是"没效果"，
而是**整个函数加载失败**（日志：`Whilst parsing command ... 未知或不完整的命令`），实测踩过一次。
所以本套调试命令一律用**逻辑加速**（改 `$period`/`$repeat`）或**快进**（连续调用 `suso.nats:main`）代替。

`tools/gen_harness.py` 里有一道自检，命中这类命令会直接拒绝生成。

## 2. 采集：一条命令出报告

```bash
node tools/collect.mjs                                   # 默认存档
node tools/collect.mjs --save "<存档目录>"                 # 换存档
node tools/collect.mjs --log "<latest.log 路径>"           # 手动指定日志
```

产物：`reports/实测-<YYYYMMDD-HHMMSS>.md` —— 断言表 + 加载期报错表 + 数值 dump + 原始标记行。
退出码：**有 FAIL 或可疑错误行 = 1**，全绿 = 0（可直接接 CI / 脚本链）。

### 日志在哪（踩过的坑）

本机是 **per-version game dir**，日志**不在存档里**，而在**版本目录**：

```
.../versions/1.21.6-Fabric 0.16.14/logs/latest.log
```

`collect.mjs` 会按顺序试：`--log` → `$NATS_LOG` → `<存档>/logs` → `<存档>/../..` → `<存档>/../../..`，
取第一个存在的。全部不存在会打印试过的路径并退出。

### 「本轮」是怎么界定的

不能一律从头扫 —— 上一轮的历史报错会把这一轮染红。锚点规则：

- **上界** = 最后一次 `harness ready`（`doom.log:internal/setup` 打印）或 `[test] begin`；
- **起点** = 上界**之前**最后一次数据包加载事件（`Found new data pack file/…` 或 `Reloading ResourceManager:`）；
- 都没有 ⇒ 0（从头扫）。

为什么不用 `harness ready` 本身当起点：**加载错误发生在加载过程中**，
而 `harness ready` 由 `minecraft:load` 标签触发，是加载**完成后**才打印的 —— 拿它当起点会把本次加载错误全漏掉。

### 报错识别覆盖中英双文本

关键词表同时含英文与**中文客户端**的本地化文本（`Whilst parsing` / `未知的方块标签` …）。
本机客户端是中文，只匹配英文会漏 —— 这是实测教训。

## 3. 判读：什么才算过

| 项 | 通过标准 |
|---|---|
| P0 断言 | 全部 `PASS`（任何 `FAIL` 都要查） |
| 加载期报错 | `可疑错误行 = 0`。**注意**：`Failed to load function` 会让整个函数失效，是最严重的一类 |
| P1 语义 | `06-进游戏实测清单.md` 三项肉眼核对通过 |
| P2 数值 | `$count` 增长且被 `$cap` 卡住；`$t` 递增；`state`/`count` 数值自洽 |
| 行为对照 | 与 `optimized` 版同场景结果一致（`sim.mjs` 已在无头层保证，实测抽查即可） |

## 4. 改完包必跑的回归四步

```bash
node tools/port.mjs            # ① 重新移植（original → ported）
node tools/optimize.mjs        # ② 重新优化（ported → optimized）
node tools/verify.mjs ../ported/suso.nats      # ③ 静态校验
node tools/verify.mjs ../optimized/suso.nats
node tools/sim.mjs 6000        # ④ 无头模拟 6000 tick
```

期望：两次 `verify` 均 **0 blocking / 0 warning**；`sim` 报 **8/8 场景一致**、`解释器错误 0`。
任何一步红，先修再谈进游戏 —— 进游戏一次的成本比这四步高一个数量级。

> 改了 `tools/gen_harness.py` 后：`python tools/gen_harness.py`（重新生成）→ `python tools/gen_harness.py --check`（应与生成器一致）。
> 动了 1.21.6 版本 jar 或怀疑 vanilla 标签时：`node _work/dump-tags.js` 重建标签权威清单（`_work/ref/vanillatags-*.txt`）。

## 5. 两个"静默杀手"（都已加了防线）

### ① 引用不存在的标签 ⇒ 整个函数加载失败

`spawn/ground/dark_end_barrens` 第 6 行引用了 `#minecraft:red_area`（原作地图包提供，本包自包含后丢失）。
表面只是"那段闪电不触发"，实际是 **`Failed to load function`，该文件所有分支一起失效**。

- 防线 1：`tools/verify.mjs` 现在会拿 `_work/ref/vanillatags-*.txt` 比对所有 `#minecraft:*` 引用，不存在即 **BLOCK**。
- 防线 2：`tools/lib/exttag.mjs` 在 port/optimize 时补一个**空标签**兜底，让函数照常加载（语义待原作确认，见 `open-questions`）。

### ② 悬空函数/谓词引用

`FN_FIX` 表（`port.mjs`）修 `basalt_deltas → dark_basalt_deltas`；`verify.mjs` 扫全部 `function`/`predicate` 引用。
外部命名空间（`general:` / `rc4:` / `src4.*:`）白名单放行，并汇总打印，便于确认夹具是否到位。
