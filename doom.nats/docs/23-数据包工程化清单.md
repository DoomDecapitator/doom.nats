# 23 · 数据包工程化清单（开发者视角）

> 问题：**从一个开发者角度，这样一个数据包「应该包含什么」？**
> 这份清单是答案，也是自检表：每层给【该有什么】【本包现状（可复核的证据）】【差距】。
> 优先级：**P0** = 影响正确性/可发布性（不补就会咬人）· **P1** = 影响可维护性与接手成本 · **P2** = 体验。
> 本包 = `doom.nats` v4（数据包驱动复刻**原版**自然生成 + Circumstance 情形引擎 + 消失层）；对照物是 demo/一次性数据包的常见形态。

## 0 · 一句话

这类包（**用数据包复刻引擎行为**）本质是两件东西：**一个把 Java 语义编译成 mcfunctions 的小编译器** +
**一个跑在 tick 上的有状态运行时**。所以它该包含的 = 编译器该有的（源 → 生成 → 漂移检测）+ 运行时该有的
（预算 / 状态生命周期 / 可观测性）+ 工程该有的（规格 / 验证 / 交付 / 兼容）。
"功能能跑"只占其中一层 —— 一次性 demo 可以只有那一层，**可被接手、可被验证、可升级的包不能**。

## 2 · 如果只做三件事

1. **覆盖层 + 机器可读 spec（L0/L1，P0）**
   目标：`tools/roster-overrides.json` / `tools/rule-overrides.json` 覆盖在"从 jar 导出的基线"之上，
   改一条 = 改两行 JSON → 重生成 → `--check` 全绿；同时自动产出「本包 vs 原版」差异表（名册/规则/覆盖三栏）。
   验收：把"发光鱿鱼改成草地生成"这类需求，只用改 JSON + 重生成就能过全部四门。
2. **每拍预算 + 自适应降级（L4，P0）**
   目标：运行时能量出"本拍还剩多少命令预算"，接近上限时**主动降批**（而不是被引擎截断后静默丢条目）。
   验收：人为把命令量压到 2× 预算，`$eff.*` 自动降档、日志 `Command execution stopped due to limit` **恒 0**、
   计数账本仍闭合（生成 = 成功 + Σreasons）。
3. **CI + 版本化交付（L7/L10/L5，P1）**
   目标：① 静态门进 CI（已做）；② 真机门跑"夜间档"（隔离实例 + `regress --reuse --minutes 1`，本机或自托管 runner）；
   ③ `CHANGELOG.md`（已做）+ storage schema 版本号与迁移函数；④ 发布 zip 带 sha256。
   验收：任何人 clone 后 `node tools/check_static.mjs` 即知产物是否漂移；升级不再靠"读 AGENTS.md 猜"。

## 3 · 三条反直觉

1. **对这种包，"差异清单 + 数字"比功能本身更重要。** 卖点是"等价于原版"，没有差异表就没有承诺；
   用户看到"水里没溺尸"，能救命的不是更聪明的代码，而是 `docs/17` 的规则表 + `reports/` 的数字链。
2. **可观测性 = 功能。** reason 码 + 计数账本 = 把"没刷出来"从玄学变成可判决的问题；
   没有它，调优只能靠猜（v4.19 的 P0-4「生产链路从不掷 `$rng`」就是靠"账本对不上"抓出来的）。
3. **"所有的刷新都可以被定义"的终点不是配置项更多，而是基线/覆盖两层 + 可 diff。**
   配置项是给玩家的缩口；**覆盖层是给作者的入口**。两者分开，才能既保证默认行为可复现，又让"改一处"成本极低。
