# 15 · 真机自动化验证（v4.3）

> 面向「怎么自己把 v4 跑起来、怎么复现今天的结论」。
> 2026-09-27 建：从此不再需要用户手敲 `/reload`、`/function` —— agent 自己起服务器、自己驱动、自己采集。

## 一、为什么要自建服务器

单人客户端**没法从外部驱动**（没有 RCON，聊天栏只能手敲），每次验证都要用户配合一轮 ⇒ 迭代速度极慢。
改用**本地 Fabric 专用服务器 + RCON + 真客户端机器人**后，一轮"改包 → 装包 → 起服 → 跑场景 → 采数"全自动，
约 3 分钟，且**不影响用户自己的单机档**（独立端口、独立世界目录）。

## 二、工具链（工作区 `_work/`，一次性搭好）

| 文件 | 作用 |
|---|---|
| `_work/mcserver/setup.mjs` | 下载 Fabric 1.21.6 服务端 + 原版 jar + Carpet + Fabric API，写 `server.properties`（RCON 25575 / offline-mode） |
| `_work/mcserver/bot.mjs` | **mineflayer 真客户端**机器人：连本地服务器当"真人"用（区块票据/玩家列表/`@a`·`distance` 选择器与真人一致） |
| `doom.nats/tools/mcrcon.mjs` | 无依赖 RCON 客户端（**一条命令一次往返**，按请求 id 配对；流水线写法会因拆包错位而卡死） |
| `doom.nats/tools/mcauto.mjs` | 主驱动：杀旧服 → 干净世界（超平/固定种子）→ 装包 → 起服 → 起机器人 → 设场景 → 等区块稳定 → 跑 `debug/all` → 采报告 |
| `_work/mcserver/…` | 服务器目录（世界、日志、`last-run.json`） |

**关键坑（都踩过）**
1. **端口占用**：旧服没杀净 → 新服 `BindException`。按**端口占用者**杀（`Get-NetTCPConnection … OwningProcess`），
   早先按命令行匹配的写法引号被吞掉、杀不掉。
2. **先杀服再删世界**：顺序反了会让新服读到被删的 `world/`。
3. **假玩家不稳**：Carpet `/player` 有时 spawn 不出来（`commandPlayer` 时序）⇒ 改用 mineflayer 真客户端。
4. **`tellraw` 不进日志**：只有真人玩家在线的客户端聊天才落盘 ⇒ 专用服务器上采集必须走 **`say`**（`debug/say_report`、`debug/say_env`）。
5. **加载错误断言**：1.20.2+ 悬空/语法错误会让**整个函数**失效且不一定可见 —— 驱动每次开局扫 `Failed to load function`，
   非 0 直接报出来（这一条当天救了一次：`check/distance` 被写坏后整条距离判定静默消失）。

## 三、当天修掉的 12 个「静默失效」

| # | 症状 | 根因 |
|---|---|---|
| 1 | 整包一次都不刷怪、无报错 | 宏占位符写成 `${x}`，MC 只认 `$(x)`（9 处） |
| 2 | 65 个选物种表加载失败 | `data modify storage X set value {…}` **缺 path** ⇒ 改 `data merge storage X {…}`（769 行） |
| 3 | 谓词 `spawn/empty_here` 加载失败 | `location_check.block.blocks[]` 不接受 `#tag` 引用 |
| 4 | 取点闸门 `$pos.ok` 恒为 0 | `pos/hit` 只写了 storage 的 `ok`，没写计分板 |
| 5 | 归因打印成 `0= 1= 2=` 空值 | 未创建的计分板条目在 tellraw 里渲染成空串 |
| 6 | `biome/detect` 加载失败 ⇒ 选不到物种 | `if biome <id>` **缺坐标**（1.21.6 必须 `if biome ~ ~ ~ <id>`） |
| 7 | `$py` 恒为 0 ⇒ 整包 y=0 ⇒ 落位全灭 | ① `data get entity @s Y` 不是合法 NBT 路径（应 `Pos[1]`）；② `random value 64..64` 退化区间被拒，而 `store result` 失败**会把目标写成 0** |
| 8 | 取点只在"命令源是玩家"时才对 | `execute at @a[…]` 少了 `as` ⇒ `@s` 不是玩家 ⇒ `data get entity @s Pos` 取不到 |
| 9 | 走位跨组累加，点位漂到 128 格外 | 源码里 `x/z` 是**组内局部变量**，每组都从 pack 原点重算 |
| 10 | 永远只刷表尾那个类别（plains 只出 glow_squid） | 7 个类别塞同一函数、各自掷一次、**后命中覆盖前者** ⇒ 改成「先均匀抽类别，再类内掷物种」（`mob/biome/<biome>/<cat>`） |
| 11 | 容量上限形同虚设 | `execute store result … if entity @e[…]` 返回的是 **0/1 不是数量** ⇒ 改成 `as @e[limit=200] run scoreboard players add` |
| 12 | 容量/消失层看不见自家生物 | roster 写的是 `nbt:{}` ⇒ 召出来的怪**没有任何标签** ⇒ 把 `Tags:[…]` 放进 summon 的 NBT |

**怎么读**：`4=落位`、`2=出 128 格`、`5/6=容量` 占绝大多数，正是原版的行为特征 ——

本包**稳态怪物数顶到上限**，说明"该刷的刷满、多余的被拒"这条链是通的。

## 五、与真正原版仍有差距的地方（不假装等同）

| 项 | 现状 |
|---|---|
| **速率** | 本包一拍一个原点（`$eff.batch` 可调，默认 6）；原版是**每区块每 tick** ⇒ 单位时间刷怪数明显低于原版。按地图需要调 `$eff.batch`/`$eff.period` |
| **类别粒度** | 原版每个类别各自一次尝试；本包一拍**均匀抽一类**（长期频率等价，瞬时分布不同） |
| **逐实体规则** | 只做到类别级落位（水中/陆生/任意）+ 光照档；`finalizeSpawn`、碰撞盒、`ANIMALS_SPAWNABLE_ON` 之外的实体特例未做 |
| **y 选择** | 原版 y 在整列均匀随机、靠 `check/block` 拒；本包用「跟随玩家 ± jitter」或「作者声明的固定带」（读不到 heightmap） |
| **光照** | 5 档区间近似（谓词读不到亮度数值、做不了采样比较） |
| **消失前置** | 读不到 `noActionTime`，消失略快（掷骰分母已按节拍放大） |
| **并集计数** | 欧氏 `distance` 表达不了 Chebyshev 方形，两模式近似（单人精确） |

## 八、v4.6：密度旋钮（作者不用碰 batch/period）

**用法**

```
/scoreboard players set $density doom.nats 0     ← 关闭自动调节（默认；等价于手工 $eff.batch=6）
/scoreboard players set $density doom.nats 120   ← 目标：每分钟约 120 只
/function doom.nats:debug/density                ← 看现状（聊天栏 + 服务器日志）
```

**控制律**（`ctrl/tick` → `ctrl/settle` → `ctrl/aimd`，每 1200 tick 结算一次）
- 测量源是 `$spawned.total`（累积量，**不被** `debug/reject_report` 清零；`$spawned` 会，所以不能用来测量）
- 低于目标 ⇒ `$eff.batch += 1`（上限 40，防止把服务器拖垮）
- 超过目标 1.25 倍 ⇒ **按比例一步收缩**：`batch = max(1, batch × 目标 ÷ 实测)`
  （一开始只降 1/分钟，从 12 降到目标要十几分钟，实测太慢，改成比例收缩后 1~2 分钟到位）

**真机验证**（常驻服务器，热载后逐 30~40 秒采样）

| 场景 | 观测量 |
|---|---|
| 白天 + 目标 30 | `batch` 6→7→8→9（往上追），`$ctrl.now` 12~18/分钟 |
| 午夜 + 目标 30 | `batch` 9→8→7→6→5（往下压），`$ctrl.now` 170~231/分钟 |
| 午夜 + 目标 30、手工把 batch 设成 12 | `batch` **12→2→1**，`$ctrl.now` 167→140→93（比例收缩生效） |
| 读数 | `[density] 目标/分钟=30 上一分钟=183 batch=5 period=4 cap.monster=70` |

**已知下界**：`batch` 最小为 1。若目标定得比"batch=1 时的实际速率"还低（本测试地形午夜约 93/分钟），
包会停在 `batch=1` 且实际速率仍高于目标 —— 这时需要作者同时手工调大 `$eff.period`
（注意 `$eff.period` 会被 Circumstance 每快照覆写，所以它属于"情形参数"，不是常驻旋钮）。

## 九、(a) 时间序列采样 + 曲线

```
node _work/timeseries.mjs --minutes 4 --every 2 [--killAt 120]
```

每 2 秒 RCON 采一次：各类别场上计数 / 累积生成 / batch / 区块数 / 全局上限 / **server mspt（tick query）**，
产出 `_work/timeseries-<时间戳>.{json,csv,svg,png}`。
**PNG 是自己手写的编码器**（zlib deflate + CRC32，无第三方依赖），这样 agent 也能"看图"确认曲线形状。

**实测（2 名玩家、午夜晚、batch 6、目标关闭）**

| 指标 | 值 |
|---|---|
| 样本 / 时长 | 120 / 4 分钟 |
| `$cnt.monster` | 稳态均值 **71.7**（全局上限 70）、峰值 77 ⇒ **顶在上限附近振荡** |
| `$spawned.total` | 1,304（累积） |
| **mspt** | 平均 **5.29 ms**、最大 5.70 ms（预算 50 ms）⇒ 本包约占 11% 预算，余量充足 |
| 清场事件 | t=121 s 执行 `kill @e[tag=doom.nats.spawned]`：70 → **26**（2 s）→ 6 秒内回到 70 |

结论：**容量链在真机上闭环** —— 刷到上限就基本停手，被清场后几秒内补满。消失层只负责"远/久的慢慢清"，
上限由 cap 负责，两者不打架。

## 十、(b) 按真实地形自动补全方块标签

```
node tools/propose_tags.mjs --save "<存档目录>" [--step 4]
```

自带的 **Anvil（region）读取器**：直接解 `.mca` → chunk NBT → `sections[].block_states`（palette + 位打包），
逐列统计「生成点下方方块」与「生成点上方方块」的分布，然后给出：
- `standable` / `spawnable_at` 的**现标签覆盖率**
- 建议补充的显式 id（按频次覆盖到 99.5%），并用一张分档表标出**哪些不该当落位面**（雪片/水/树叶/告示牌…）

**首跑就抓到真问题**（测试地形是雪原）：

| | 扩标签前 | 扩标签后 |
|---|---|---|
| `standable` 覆盖率 | **3.7%** | **43.9%**（且"可当落位面"待补条目 = **0**） |
| `spawnable_at` 覆盖率 | 100% | 100% |

那 3.7% 的原因很具体：该地形里最多的可站立面是 **`ice` / `packed_ice`（占 40%）**，而默认标签里**没有它们**
（原版冰是完整方块，能站能刷）。剩下的 56% 是水/雪片/树叶/蕨 —— **本来就不该能站**，
所以补到 43.9% 就是"该覆盖的全覆盖了"。

> 用法：地图成型后跑一次，把「建议补充_可当落位面」的 id 追加进
> `v4/doom.nats/data/doom.nats/tags/block/standable.json`（改生成器而不是改包），再 `lint` + 装包即可。

## 十一、(c) 压力测试：地图的性能安全线

```
node _work/stress.mjs --batches 6,24,40,80,160 [--settle 12 --sample 30]
```

逐档设 `$eff.batch` → 稳定后采样 mspt / 吞吐，产出 `_work/stress-<时间>.json` 与建议值。

**第一轮（默认 gamerule）×**：吞吐在 batch≈40 就**饱和**（点/tick 卡在 ~76），但 mspt 只有 ~10ms。
现象说明瓶颈不在性能，而在**原版每 tick 的命令链上限** `maxCommandChainLength`（默认 65536）。

**验证**：把 `gamerule maxCommandChainLength` 调到 1,000,000 后重测 ⇒ 吞吐线性上升，假设成立：

| batch | mspt（均/峰） | 点/tick | 尝试/tick | 备注 |
|---|---|---|---|---|
| 40 | 9.7 / 9.9 | 75 | 10.0 | 默认 gamerule 下已经是天花板 |
| 160 | 24.1 / 24.9 | 300 | 40.0 | 60% 预算内 |
| 400 | **50.9 / 52.5** | 730 | 97.3 | **超预算**（50ms） |

**给地图作者的结论（本机、2 名玩家、雪原超平世界）**
1. 想让每 tick 的尝试量接近原版，**必须调大 `maxCommandChainLength`**（否则 ~10 尝试/tick 封顶）。
2. 之后用 `$density`（每分钟目标只数）或直接 `$eff.batch` 控制强度；**mspt ≤ 30（预算 60%）** 对应
   本机约 `batch ≤ 200`（≈50 尝试/tick）。上表可作为起点，换机器/换地图请重测一次。
3. 控制器的 `batch` 上限已参数化：`$ctrl.maxBatch`（默认 40），配合上面的 gamerule 一起调。

**其它维度**：地狱/末地在测试世界里还没生成过区域文件，`propose_tags` 暂无法统计，
所以先按已知完整方块族预置（`#minecraft:base_stone_nether` / `#minecraft:nylium` / `#minecraft:wart_blocks`
+ shroomlight/glowstone/gilded_blackstone/ancient_debris/sculk 家族等）；地图做完再跑一次工具复验。
现 `standable` 共 83 条、`spawnable_at` 100% 覆盖、该地形"可当落位面"待补 = 0。

## 十二、v4.11：移除一律走 void_kill（用户指出的保真问题）

**用户观察**：清场时用 `kill` 不太合适，应该用原作里的 `void_kill`，并且要建立清理机制。**完全正确**，这是保真问题：

- 原版**消失 / 超距移除**调用的是 `Entity.discard()` —— 静默移除，**不掉战利品、不给经验、不触发死亡逻辑**；
- 而 `kill` 等价于「被打死」：掉战利品、给经验、触发死亡处理（僵尸烧掉、凋灵玫瑰、进度等）。
- 原作 `recovered/doom.nats/.../void_kill.mcfunction` 就一行：`tp @s ~ ~-500 ~`（把实体丢到世界下方，下一 tick 因出界被静默 discard）。

**实现**

- `util/void_kill`：`tp @s ~ ~-500 ~`（与原作一致）。
- 消失层全面改用它：硬消失（`distance=129..`、`water_ambient` 65 格）与概率消失（1/`$despawn_dice`）都不再 `kill`。
- 新增**清理机制** `debug/clear`：静默清掉本包生成的全部生物（保留 `doom.nats.persistent`），数量报到聊天栏与服务器日志。
- 自动化脚本（`_work/timeseries.mjs --killAt`）也改调 `debug/clear`，不再用 `kill @e[…]`。

**真机物证**（常驻服务器）

| 观测 | 值 |
|---|---|
| `debug/clear` 移除生物数 | **96** |
| 该操作**新增**掉落物 | **0** |
| 清场前场上已有掉落物 | **476** ← 正是此前用 `kill @e[…]` 清场留下的战利品（反证） |
| 遗留掉落物处理 | 同样 `tp ~ ~-500 ~` 丢入虚空，场上归零 |

也就是说：用户凭直觉指出的问题，在数据上被证实了（476 个掉落物就是物证）。


## 十三、v4.10：簇（cluster）模型 —— 回答「怪物的簇有没有设计？」

有，而且是按 `NaturalSpawner.spawnCategoryForPosition` 的源码结构 1:1 复刻的。原版一次"刷怪尝试"并不是刷 1 只，而是**先打 3 个簇（group）尝试**，每个簇里再刷一串。

**原版结构（源码级）**

1. 一次尝试最多 **3 个 group**；
2. 每个 group 开始时 x/z **重置**回原点（`x = originX; z = originZ`）；
3. 先按 `ceil(rand*4)` 取一个 `groupSize`，**但**在真正挑中物种时会**重算一次**：`groupSize = minCount + rand(1 + max - min)`；
4. 物种**每个 group 只挑一次**（且必须先过距离检查）；
5. 组内后续个体：`x += nextInt(6) - nextInt(6)`、`z += nextInt(6) - nextInt(6)` —— 位移**组内累加**（所以一簇是会"拉长"的）；
6. 一旦 `spawned >= mob.getMaxSpawnClusterSize()` ⇒ **直接 return**，整次尝试结束（不是只结束这个 group）。

**簇上限（`getMaxSpawnClusterSize`）**：扫 1038 个实体类，**只有 8 个覆盖**，其余全用 `Mob` 默认值 4。

| 实体 | 簇上限 |
|---|---|
| 默认（Mob，含僵尸/骷髅/苦力怕/蜘蛛/末影人…） | **4** |
| `AbstractFish`（鳕鱼等） | 8 |
| `AbstractSchoolingFish`（鲑鱼等） | `getMaxSchoolSize()`（鲑鱼 5） |
| `AbstractHorse`（马/驴…） | 6 |
| `Wolf` | 8 |
| `Pillager` / `Ghast` / `HappyGhast` | 各自覆盖值 |

**本包实现**

- `spawn/group`：一个 group 的主体；`$grp.sel`（是否已选物种）、`$grp.sized`（是否已按 min/max 重算 size）、`$grp.stop`。
- `spawn/walk`：组内位移累加 `nextInt(6)-nextInt(6)`；**每个 group 重置**、组内**不加**重置。
- `spawn/regroup`：宏函数，按 `$grp.stop` / `spawned >= clusterMax` 结束整次尝试（对齐原版的 `return`）。
- `$dbg.clusterMax` 暴露当前物种的簇上限；`$att.spawned` / `$att.stop` 记录每次尝试结果。
- 物种表里每行都带 `cluster:` 字段（`gen_ctm_mobs.mjs` 的 `CLUSTER` / `clusterOf`），生成期就把上限钉死。


### 十二·补：void_kill 对照实验（40 只蜘蛛）

上面的「96 只、0 掉落」是清场路径的证据。为了排除偶发，又做了一组**定点对照实验**（同上常驻服务器，RCON 直连）：

| 步 | 操作 | 存活 | 掉落物 |
|---|---|---|---|
| 0 | 先把场上掉落物全部丢虚空，取基线 | — | 2（历史遗留） |
| 1 | 在同一点 `summon` 40 只带本包标签的蜘蛛 | 40 | 2 |
| 2 | 等 12 秒（含原版堆挤/挤压伤害的自然损耗） | 36 | **2（无新增）** |
| 3 | `execute as @e[tag=cramtest] at @s run function doom.nats:util/void_kill` | **0** | **2（无新增）** |

结论：**移除路径不产生任何掉落物**（第 3 步 36 只全清、掉落物计数不变）。第 2 步少掉的 4 只是原版机制本身造成的（堆挤伤害/概率消失），与本包的移除语义无关。

另附一条现场观察，用于区分「掉落物从哪来」：常驻服务器上另有一个**真人客户端**（`Doom_Flare`）在线，场上散落的 `string` / `blue_egg` 掉落物是**那些生物被玩家正常击杀**留下的 —— 这正是原版行为，与清理机制无关；用 `void_kill` 清理的那一次，掉落物计数纹丝不动。
