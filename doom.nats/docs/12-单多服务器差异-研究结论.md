# 12 · 单 / 多 / 服务器环境的刷怪差异（源码级结论）

> 来源：研究员 A 的 `_work/research/B-源码细节报告.md`（382 行，§0–§10），
> 证据链为 client.jar 1.21.6 → client_mappings → named.jar → Vineflower + `javap -c`，
> 并用 **server.jar 做跨端字节核对**（ServerChunkCache / NaturalSpawner / SpawnState / MobCategory /
> EntityType / MobSpawnSettings 等 8 类 sha1 完全一致）⇒ **客户端结论可直接用于专用服务器**。

## 一、`getNaturalSpawnChunkCount()` 的确切定义（关键）

- 实现：`DistanceManager.naturalSpawnChunkCounter = FixedPlayerDistanceChunkTracker(8)` ——
  **每个玩家所在区块的 17×17（半径 8 区块，Chebyshev 距离）正方形之并集大小**。
- **与 `view-distance` / `simulation-distance` 无关**；多玩家时重叠区块只计一次。
- 因此 `cap = maxInstancesPerChunk × 并集 / 289`（int 截断）——**单人恰好 70，是稳态特例，不是常数**。
  多人大服会按人数放大上限。
- 对 v4 的影响：我们的 `circ/scan_chunks` 扫描的是**首个玩家的 17×17** ⇒
  **单玩家精确**（上限 289）、**多玩家低估**。已在生成器注释与 `docs/11` 标注；
  精确并集需要「逐玩家扫描 + 去重」或改以绝对坐标做 dx/dz 盒式判定（待办）。

## 二、1.21.6 的一处源码缺陷：`spawnFriendlies` 恒为 true

`ServerChunkCache.setSpawnSettings(boolean)` 的字节码是**自赋值**：
`spawnEnemies = arg; spawnFriendlies = spawnFriendlies;`
⇒ 只能关掉敌对生成；**被动生物永远进入候选**（`MobCategory.CREATURE.isPersistent = true`），
且只在 `gameTime % 400 == 0` 时参与一次。
⇒ v4 已加入 `$creature_gate`（`$snap.daytime % 400`）以复刻该节拍。

## 三、刷怪链条（全部条件，缺一不可）

区块在 **8 区块半径**内 ∧ 是 **ticking chunk**（`ChunkLevel ≤ 32`，实体刻 ≤ 31）∧
附近有**非旁观玩家且在 128 格内** ∧ `canSpawnEntitiesInChunk` ∧ `doMobSpawning = true`。

## 四、消失公式（可直接照抄实现）

```
noActionTime > 600 && random.nextInt(800) == 0 && d² > 32² && removeWhenFarAway(d²)  → 消失
硬消失：d² > despawnDistance²（128²；WATER_AMBIENT 为 64²）
近玩家（d² < 32²）会把 noActionTime 清零；d² ≥ 32² 时不再清零
```

## 五、spawn cost（1.16+ 的刷怪密度机制）

- 公式：`charge × Σ(q / r) ≤ energy_budget`（**1/r 三维权重，无衰减**；每 tick 重建，生成后即时加 charge）。
- 原版非空定义**只有两个群系**：`warped_forest`（末影人 1.0 / 0.12）、`soul_sand_valley`（0.7 / 0.15）
  —— 与我们从 jar 导出的 `biomes.json` 完全一致（该导出已验证：仅这两个群系带 `spawn_costs`）。

## 六、单机 / 专用服务器的差异（影响"关掉自然生成"的验证方式）

- 专用服务器：`pause-when-empty-seconds` 默认 **60 秒**后停止 tick ⇒ 无人在线时**完全不刷怪**。
- 单人客户端：暂停菜单时 `tickPaused()` ⇒ **同样完全不刷怪**。
- ⇒ 实测时必须保证游戏处于运行态（不要开菜单），否则所有"不刷怪"的结论都不可信。

## 八、为什么"精确并集"暂不实现（技术说明）

原版的 17×17 是 **Chebyshev 距离**（方形）；而数据包里唯一能"相对执行位置"判定的选择器是
`distance`（**欧氏球**），**无法表达方形**，两者不能互相替代（欧氏 128 会漏掉方形的四角，欧氏 181 又会过计）。

要精确数出并集，必须按下面的路走：

1. 取得每个候选区块的**绝对坐标**；
2. 用 `@a[x=<bx-128>,dx=257,z=<bz-128>,dz=257]` 这类**绝对盒式选择器**判定"该区块是否被任一玩家覆盖"；
3. 绝对坐标只有运行期才算得出 ⇒ 每个点都要一次宏调用 ⇒ **约 289 次宏/快照**。

结论：**可行但代价明显**。因此 v4 先提供两种可选近似（`$chunks_mode`）：

| 模式 | 行为 | 单人 | 多人 |
|---|---|---|---|
| `0`（默认） | 只扫首个玩家的 17×17 | 精确 | **低估**（保守，刷怪偏少） |
| `1` | 逐玩家扫描后累加 | 精确 | **高估**（重叠被重复计数） |

精确并集记为待办；在单人地图（CTM 的常见形态）下，两种模式都**精确等于原版**。
