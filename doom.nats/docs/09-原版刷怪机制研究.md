## 二、可复现的反混淆工作流

1. 从 mappings 站取 `named ↔ intermediary`（例：`net.minecraft.world.level.NaturalSpawner` ↔ `class_1948`）。
2. **用行为特征在官方混淆 jar 里定位类** —— 这一步是真正的难点：
   - ❌ 按「常量池里引用了 `cap`」扫 → 只找到 5 个类，**漏掉目标**；
   - ✅ 按**描述符**扫 `Ldne;`（`LocalMobCapCalculator`，签名特征鲜明）→ 一次命中 4 个：
     `aty`(调用方) · `dnf`(本体) · `dnf$d`(内部类) · `dne`(它自己)。
   - 教训：类型**只出现在方法描述符**里时，常量池里没有 `CONSTANT_Class` 条目。
3. `javap -p -c` 读字节码，用**常量与调用链**对照公开文档。

映射链最终确证：

```
dgu (1.21.4 官方名)  ↔  class_1948 (intermediary)  ↔  net.minecraft.world.level.NaturalSpawner
dnf (1.21.6 官方名)  →  方法签名与 mappings 页逐条对应（见下）
```

## 五、完整流程（据上述来源重建）

1. **调度**：每 tick，`ServerChunkCache` 统计「可刷怪区块数」，对每个合格区块调用 `spawnForChunk`。
   区块合格 = 与 random tick 同一套判定（有玩家附近）。
2. **建状态**：`createState(chunkCount, 全部实体, …)` → `SpawnState`（按类别计数 + per-player cap 计算器）。
3. **选类别**：`getFilteredSpawningCategories` 过滤（`spawnMonsters`/`spawnFriendlies`/难度/是否活跃）。
4. **取点**：`getRandomPosWithin` —— **x/z 在区块内完全随机**，y 取「该列最高方块之上到世界最低限」之间的随机值。
   ⇒ 降低天花板高度（perimeter）能显著提高刷怪率，就是这么来的。
5. **尝试 pack**：每类别最多 3 次；命中点若是「不透明完整方块」则取消后续尝试。
6. **逐只生成**：位置 ±5（三角分布）偏移；先按**第一次尝试位置**的合格表加权选物种（minCount..maxCount 来自群系 `spawners`），
   之后同 pack 内同物种；后续尝试若该物种不能在当前位置生成则失败。
7. **合法性**：24 格内无玩家/出生点 · 未超 cap（**不检查群体大小**，所以可能超）· 碰撞盒不与方块/实体相交 ·
   非被动须在 128 格球内（鱼 64）· 生成面条件（非完整碰撞盒、非红石元件、非流体、非 `prevent_mob_spawning_inside`、不伤害该生物）·
   宿主怪物另有光照与方块白/黑名单。
8. **消失**：128 格球外立即消失；>32 格持续 30 秒（高光照 10 秒）后每 tick 1/800 概率消失；
   `PersistenceRequired` / 命名牌 / 结构生成 / 乘骑 / 有物品栏 ⇒ 不消失**且不计入 cap**。

## 六、数据包能复刻到什么程度

| 原版环节 | 数据包 | 手段 / 缺口 |
|---|---|---|
| 群系刷怪权重表 | ✅ **完全** | 覆盖 `data/minecraft/worldgen/biome/*.json` 的 `spawners`（**本来就是这个机制**） |
| 光照判定 | ✅ 可读 | `location_check` → `light.light{min,max}`（suso.nats 的 `dark.json` 已在用 0..3） |
| 生物群系 / 结构 / 维度 / 时间 | ✅ | 同一个 `location_check` 谓词 |
| mobcap | 🟡 近似 | 能按类别计数、能比 70/10/15，但**拿不到 `spawnableChunkCount`（289 区块缩放）与 `LocalMobCapCalculator` 的 per-player 统计** |
| 落点几何 | 🟡 近似 | 「区块内随机 x/z + 从表面取 y」可用「玩家周围 17×17 区块内随机取点」近似；读不到 ticking chunk 状态 |
| 落位合法性 | 🟡 近似 | 只有方块标签（`solid`/`free`）；碰撞盒、`prevent_mob_spawning_inside`、伤害免疫判定都缺 |
| pack（3 次 + ±5 + min/max） | 🟡 近似 | 可自己写递归 + `minCount..maxCount`（数据就在 biome JSON 里） |
| `finalizeSpawn` / 族群数据 | ❌ | 每类生物要手写 |
| 区块 tick 调度 | ❌ | 只能自定频率 |

**推论**：
1. 想还原**原版分布**，正解是**不要复刻**——覆盖 biome JSON 即可，逻辑白送；
2. 只有在「要原版感 + 要自定义敌人」且不能装 mod 时，才值得用数据包模拟，并接受上表 ❌；
3. 要**完全一致**只能上 mod（包装/替换 `NaturalSpawner`、注册自定义 `SpawnPlacementType`）。

## 七、对 suso.nats 的对照结论

| 维度 | 原版 | suso.nats | 评价 |
|---|---|---|---|
| 上限 | `70 × chunks ÷ 289`，分类别 | 128 格内计数 ≤ **70**（`$cap`） | 抄了 cap 数字，但**没有 289 缩放、不分类别** |
| 取点 | 区块内随机 x/z，y 从表面起随机 | 以玩家为球心：方位均匀 + 俯仰偏 0° + 距离 `27+3s`（27..120） | **最本质的差异**：观感更像"环境里的"，但分布形状完全不同 |
| 玩家禁区 | 24 格球 | 距离下限 27 格 | 等效近似（略保守） |
| 光照 | `方块光=0 且 天空光≤7`，且 `≤ random(0..7)`（**概率**） | `location_check` 光照 0..3（**确定**） | 近似，且更严格 |
| 成群 | 3 次尝试 + ±5 三角偏移 + min/max | 每次触发 `$repeat`=10 次独立尝试 | 机制不同，效果相近 |
| 落位判定 | 碰撞盒 + 方块黑/白名单 + 伤害免疫 | 只看 `solid`/`free` 标签 | **最大短板**（会刷在墙上、岩浆边） |
| mobcap 是否适用 | cap **不适用于** `/summon` | 同理 ⇒ **不受原版 cap 约束**，只受自己计数 | 两者并不冲突，可叠加 |
| 消失 | 128 格瞬灭 + 1/800 概率 | **同一套原版规则仍然生效**（它们就是普通怪物） | suso.nats 不必自己做 despawn —— 这条被原版兜住了 |

⇒ suso.nats 的定位很清楚：用「几何采样 + 群系查表」换到了**NBT 级的遭遇编排能力**，
代价是放弃了原版的落位合法性判定；而 70 / 128 / 27 这几个数字说明原作确实参照过原版参数。

### 9.2 与 wiki 描述的对照与修正

| # | 项 | wiki 说法 | **源码实况** |
|---|---|---|---|
| 1 | 取点 y 坐标 | 「最高方块之上到最低垂直限之间随机」 | `Mth.randomBetweenInclusive(random, level.getMinY(), 地表+1)` ⇒ **闭区间内均匀**，并不偏向表面 |
| 2 | pack 内偏移 | 「±5 三角分布」 | `x += random.nextInt(6) - random.nextInt(6)` ⇒ **累加游走**（每只都在前一只基础上偏移），可漂移出 40 格 |
| 3 | 群体大小 | 「先定物种再定数量」 | 初始 `ceil(rand*4)` ∈ {0..4}；**首次成功选定物种后重算**为 `minCount + rand(1 + maxCount - minCount)` |
| 4 | spawn cost 判定 | `sum(电荷÷距离) × 新电荷 < 最大潜力` | `PotentialCalculator.getPotentialEnergyChange(pos, charge) <= energyBudget` ⇒ **`<=`，不是 `<`** |

### 9.3 关键实现（源码确证）

**取点**：`x/z` 在区块内 `nextInt(16)` 随机；`y ∈ [getMinY(), 地表+1]` 均匀随机；命中起点方块若是「红石导体」则整个 pack 取消。

**pack**：每类别最多 **3 次**；内层循环把位置 `x += nextInt(6)-nextInt(6)`（同理 z），逐只尝试；
每只成功后 `snapTo(x+0.5, y, z+0.5, random*360°, 0°)`（生成时**随机偏航、俯仰 0**）；
`getMaxSpawnClusterSize()` 达标即提前返回，`isMaxGroupSizeReached()` 达标则跳出；
族群数据 `SpawnGroupData` 沿 pack 传递（`finalizeSpawn` 的返回值）。

**合法性链**（任一步失败即放弃该只）：
1. `distSq <= 576.0` ⇒ 拒（**24 格球**，平方比较）；
2. 世界出生点 24 格内 ⇒ 拒；
3. `!canSpawnFarFromPlayer() && distSq > despawnDistance²` ⇒ 拒（**128 格**，仅对"不能远离玩家生成"的类型）；
4. 类别是 `MISC` ⇒ 拒；`!canSummon()` ⇒ 拒；
5. `canSpawnMobAt` —— 该物种必须在**当前位置的刷怪表**里（结构优先：下界要塞用固定表，否则 `chunkGenerator.getMobsAt(biome, structures, category, pos)`）；
6. `SpawnPlacements.isSpawnPositionOk(type, level, pos)` —— 地面/水面类型匹配；
7. `SpawnPlacements.checkSpawnRules(type, level, NATURAL, pos, random)` —— 光照等；
8. `level.noCollision(type.getSpawnAABB(...))` —— 碰撞盒不能撞；
9. `isValidEmptySpawnBlock` —— 非完整碰撞盒、非信号源、非流体、不在 `PREVENT_MOB_SPAWNING_INSIDE`、不是对该生物的伤害方块。

**mobcap（SpawnState）**：

```java
// 全局：严格小于，整数除法
cap = category.getMaxInstancesPerChunk() * spawnableChunkCount / MAGIC_NUMBER;   // 289 = 17²
允许 = mobCategoryCounts.get(category) < cap;

// 每玩家：交给 LocalMobCapCalculator
允许 = localMobCapCalculator.canSpawn(category, chunkPos);
```

`afterSpawn` 同时做三件事：`spawnPotential.addCharge(pos, charge)` · `mobCategoryCounts.addTo(cat, 1)` ·
`localMobCapCalculator.addMob(chunkPos, cat)`。

**spawn cost**：`SpawnState.canSpawn` 取该位置群系的 `MobSpawnCost`（来自 biome JSON 的 `spawn_costs`）；
无成本定义则直接允许；有则比较 `PotentialCalculator.getPotentialEnergyChange(pos, charge) <= energyBudget`。

### 9.4 对复刻的最终影响

- 用源码核对后，第六节的可行性矩阵**不变**：mobcap 需要 `spawnableChunkCount`（数据包拿不到 289 缩放）；
  取点需要「区块 + 高度图」（数据包只能近似）；合法性链的第 6–9 步全是数据包无法表达的（碰撞盒、`isSignalSource`、伤害判定、`PREVENT_MOB_SPAWNING_INSIDE` 之外的流体/危险方块规则）。
- 但**复刻的"可模仿部分"更清楚了**，如果要写数据包版，应当照抄的是：
  ① 距离下限 **24** 格（平方 576）；② 上限 **128** 格；③ 类别上限 **70 / 10 / 15**；④ 群体大小 `minCount..maxCount`（biome JSON 里就有）；
  ⑤ 偏移用 `nextInt(6)-nextInt(6)` 的累加游走（而不是"从中心一次偏移"）——这一条常被写错。
